# Version 1.6 — Rustcraft in the browser

v1.6 adds a web build that runs in a browser on Mac and Windows, from the same repo and the same crate. It follows Eaglercraft's approach (Kenzo's decision): the game logic stays as it is, and the differences between a computer and a browser live behind small traits with `#[cfg(target_arch = "wasm32")]` implementations. Same Milestone rules as CLAUDE.md (Step 0, small commits, tests, one PR per milestone, stacked, at most one screenshot), plus:

- **Target:** `wasm32-unknown-unknown`, stable Rust, wasm-bindgen. No SharedArrayBuffer, no nightly toolchain, no build-std, no COOP/COEP headers, so any static host works. Still no game engine (§2).
- **No cfg in game logic:** platform differences live in `src/platform/` (storage and files, tasks, time, logging, environment, asset loading) and in the few modules that are wasm-only (`web/`). Native keeps `std::thread`, `crossbeam-channel` and `std::net` as they are.
- **The split (M72):** the browser main thread is the client (`client.rs`): winit on a canvas, wgpu on WebGPU with WebGL2 as the fallback, egui, kira, input and the per-frame mesh upload. The server (`server.rs`) runs in a dedicated Web Worker with its own wasm instance: chunk scheduling, lighting, ticking, `game/`, Distant Terrain's tile maker and saves. Client and server talk through the `net/` transport trait with a new `WorkerTransport` (same messages, bincode + lz4_flex, `postMessage` with transferable ArrayBuffers). The in-process transport stays on wasm as "single thread mode" (`?single-thread`). Generator workers (default `min(3, hardwareConcurrency − 2)`, at least 1) are spawned by the server worker; mesher workers (default 2–4) by the client.
- **The main thread never blocks:** every channel is polled with `try_recv` or the equivalent. Uploads per frame are capped by a time budget (starts at 2 ms, a measured starting value, configurable, recorded in `docs/DECISIONS.md`). Chunk requests go nearest first, inside the view frustum first. Render distance ramps from 4 to the setting after spawn, teleport or a dimension change.
- **Never lower** render distance, world height or visual quality to pass a gate (§4); stop and report.
- **Assets:** the web build serves only the repo's own assets (`assets/` minus `assets/vanilla/` and `assets/downloads/`). Mojang's files, Kenzo's five packs and the mod jars never go into the web build output (§9 v1.5). A setup screen asks for the vanilla layer (folder or .zip, checked like `scripts/check-vanilla.sh`) and optionally the packs, and stores them in OPFS as the same layers native uses. Until the vanilla layer is loaded only the Vanilla style over Kenzo's assets is offered; missing textures show the magenta/black checkerboard, never replacement art.
- **Left out of the wasm build:** LAN (Open to LAN and Multiplayer hidden), Lua mods and Fullbright (the Mods screen says "Lua mods aren't available in the browser version"; its M66 routing of resource packs and data packs still works), and the native-only dev tools (`--perf-test --native`, `--texture-audit`, `--lan-test`, `--shot`; the Texture Viewer stays). Distant Terrain stays in, default Off on wasm until M73 measures it, its cache capped by `navigator.storage.estimate()`.
- **Golden hashes don't change** in this checkpoint (§7 rule 14). The native perf gate (§7 rule 12) runs at the end of every milestone against the fixed baseline; never `--update-baseline`.
- **Browser measurements:** Chrome driven by Playwright, headed so it uses the real GPU, on Kenzo's M4 (the machine the sessions run on).

### - [x] M70 — The platform layer

One line per item in the first commit body and the PR.

  - Move every Step 0 use behind them; `main.rs` becomes a native-only entry (`native.rs`).
  - cfg out for wasm32: `mlua` (the `mods::lua` module gets a stub with the same types that never starts), `libc`, `env_logger`, `pollster`, `arboard` (egui-winit without the clipboard feature), LAN (`net::lan` stub; Multiplayer and Open to LAN hidden), kira streaming (long sounds are decoded whole).
  - Add `cargo check --target wasm32-unknown-unknown` and `cargo clippy --target wasm32-unknown-unknown -- -D warnings` to §7 rule 6, `.githooks/pre-commit` and CI.

- **Done when:** the tests pass, golden hashes are unchanged, both wasm32 checks pass, and the native perf gate passes. *Status:* done; the native gate missed against the 120 Hz baseline on a 60 Hz display and was accepted by Kenzo on the v1.5.0 comparison (PR #79). ### - [x] M71 — The browser client
- **Goal:** the game runs in Chrome on the M4 from a local static server, with the in-process server.
- **Step 0:** the size of the wasm output (raw, after `wasm-opt -O3`, gzipped) and the time to the setup screen and to the title screen on the M4, with the wasm build's first successful frame.
- **Tasks:**
  - `scripts/build-web.sh`: wasm-bindgen + `wasm-opt -O3` into `target/web/`, plus `web/index.html` and a small JS loader in `web/`. It refuses to copy anything from `assets/vanilla/` or `assets/downloads/` and checks its output for them. `scripts/serve-web.sh`: a local static server reachable on the LAN, which prints its URLs.
  - WebGPU first, WebGL2 if it's missing; under WebGL2 any style or Shaders effect that needs WebGPU-only features turns off, with a note in Video Settings.
  - Async start-up: the GPU, the asset loads and the layers (`platform::assets`) behind a loading screen. `assets.rs` gets a web asset root (fetch over HTTP or one archive packed at build time).
  - The asset setup screen: the vanilla layer (folder or .zip, checked like `scripts/check-vanilla.sh`) and optionally the packs, stored in OPFS as the same layers native uses; Resource Packs also accepts a file picker or drag and drop later. Until the vanilla layer is loaded only Vanilla over Kenzo's assets is offered.
  - Input: pointer lock with `unadjustedMovement` where supported; losing it (Esc, tab switch, alt-tab) opens the pause menu; the context menu is blocked on the canvas; keys the browser takes get a documented alternative in Controls (F12, Shift+F12 and others); in fullscreen on Chromium the Keyboard Lock API lets Esc and F-keys through. Keys the browser keeps (Cmd+W, Ctrl+W, Cmd+Q, Ctrl+T) are documented, not fought.
  - Audio starts (`AudioContext.resume`) on the first click or key press; the title screen shows "Click to start" until then.
  - `options.ron`, packs and `texture-marks.ron` persist in OPFS (main-thread async or a small worker; saves stay in-process until M72).
- **Tests:** unit tests for the URL query parser, the vanilla layer check (fake complete and incomplete layouts, like `check-vanilla.sh`), and the build script's refusal (a fake `assets/vanilla` file in the output fails the check). A Playwright script (`web/test/smoke.mjs`) loads the page headed and checks the canvas draws and the console has no errors.
- **Source of every number:** no gate yet; the size and time numbers are measured, not targets.
- **Done when:** Chrome on the M4 shows the setup screen, then the title screen; creates a survival and a creative world; plays with sound, mouse look, breaking and placing, and the inventory; options persist across a reload; the native perf gate passes. Screenshot: the title screen in Chrome (Playwright).

### - [ ] M72 — The Eaglercraft split
- **Status (what is built and what isn't):** built and tested: `WorkerTransport` (+ the server-and-two-clients agreement test over worker-shaped connections), generator Web Workers (chunks equal native's for the golden seeds in all three dimensions), worlds saved to OPFS and restored (Playwright: save, reload, 8 files byte-identical, world reopens), world .zip export/import both ways (a Chrome export opens with native `Game::open`, a native-made world opens in Chrome). **Not built:** the server in its own Web Worker, mesher workers, the 2 ms upload budget, frustum-first requests, the render distance ramp, and OPFS sync access handles (saves go through the main thread's async writer). See the PR for why and what's next.
- **Goal:** the server in a Web Worker, generation and meshing in more workers, saves in OPFS.
- **Step 0:** with M71's single-thread mode, the per-frame cost of the server tick, chunk generation and meshing on the main thread at render distance 9 (ms per frame, from the F3 numbers), and the longest frame.
- **Tasks:**
  - `WorkerTransport` beside the TCP and in-process transports: the same messages, bincode + lz4_flex, `postMessage` with transferable ArrayBuffers. The in-process transport stays as `?single-thread`.
  - The server worker (its own wasm instance) runs `server.rs`; generator workers (default `min(3, hardwareConcurrency − 2)`, at least 1) receive (seed, dimension, chunk position, world settings) and return the chunk, bit-identical to native.
  - Mesher workers (default 2–4, spawned by the client) receive a section, its neighbor borders and the block/model tables built by `look::Look`, and return vertex and index buffers as transferables. When the packs or style change, the client sends the new tables to every mesher before remeshing.
  - Every channel polled with `try_recv` or the equivalent. Per-frame upload capped by a time budget (2 ms start, configurable, recorded in `docs/DECISIONS.md`). Chunk requests nearest first, in the frustum first. Render distance ramps from 4 to the setting after spawn, teleport or a dimension change.
  - OPFS `Storage` backend with sync access handles in the server worker: region files, `level.ron`, `playerdata/`, advancements, the Distant Terrain cache; `options.ron`, packs, `texture-marks.ron` and the vanilla layer too. Worlds export and import as .zip with the folder layout of native saves, from the Select World screen.
- **Tests:** the protocol through a WorkerTransport-shaped channel (serialize, copy, deserialize) with a server and two clients that agree (§7 rule 10); chunks from the generator-worker path equal native's for the golden seeds in all three dimensions; save, reload, identical world in Chrome (Playwright: quit to title, reopen, compare block hashes).
- **Source of every number:** the 2 ms upload budget and the worker counts are Kenzo's starting values, to be measured in M73. The ramp start (4 chunks) is Kenzo's.
- **Done when:** a world saves and reopens in Chrome; a world exported from Chrome opens in the native .app and a native world opens in Chrome; the server and workers show as separate threads in Chrome's performance panel; golden hashes are unchanged; the native perf gate passes. Screenshot: the performance panel showing the separate threads, or the world in Chrome.
